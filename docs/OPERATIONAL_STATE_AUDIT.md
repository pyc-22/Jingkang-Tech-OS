# 房态 / 技师状态只读审计与纠正流程

本目录的审计脚本只执行 `SELECT`，不连接生产、不更新业务表。它复用 `OperationalStateService` 的口径：活动服务和已完成但仍有有效未结订单的服务占床；订单作废/取消或整单红冲后释放；仅退款重结不释放。

## 使用顺序

1. 在目标数据库的只读连接执行 `tools/regression/operational-state-audit.sql`，将每个结果集保存为带时间戳的文件。
2. 由门店逐条核实 `VOID`、`LINK_ORDER`、`ASSIGN_BED`、`KEEP`，尤其核实未结算服务清单和 `bed_count` 与实际床位配置。`zz-wanda/777` 的床位配置异常只记录为 `BED_CONFIG_MISMATCH`，不在本次纠正脚本中自动停用或删除床位。
3. 仅在核实结果、目标门店、操作人和原因都已确认后，复制 `tools/regression/operational-state-repair-template.sql`，填写计划行，先执行到 `ROLLBACK` 检查影响行数，再由负责人改为 `COMMIT`。

## 审计输出

脚本分别输出：

- 房间事件状态与实时派生状态不一致；
- 活动/未结服务缺床、错房、同床重复占用；
- 服务与订单链接缺失、已取消/整单红冲链接仍被当作有效结算；
- 技师参与记录与服务状态不一致；
- 会员卡支付/退款缺 `wallet_id`、钱包余额与流水不平、消费流水找不到有效订单。

每个结果集都带 `suggested_action`，它只是候选标记，不是自动修复结论。结果数量和明细必须随门店核实记录一并归档。

## 纠正与回滚

纠正模板在事务内先写入 `operational_state_repair_backup` 快照，再追加 `operational_state_repair_event` 和 `audit_log` 事件，原订单、服务、支付、退款和历史审计行不删除。`LINK_ORDER` 只新增服务-订单关联，`ASSIGN_BED` 只修正当前服务床位，`VOID` 按现有服务作废语义补齐作废元数据，`KEEP` 只记录核实结论。

模板默认停在 `ROLLBACK`。提交前检查备份行数、计划行数、冲突检查和结果集；发生任何异常由数据库事务回滚。提交后的回退使用同一 `run_id` 的备份快照生成反向纠正事件，不能删除原始业务历史，也不能直接删除床位。

本次不新增 Flyway 迁移：审计/纠正表仅由人工复核后的运维脚本按需创建，统一状态服务和正常业务路径不依赖这些表。
